# PR 만들기

## 순서

1. **브랜치 확인**: 지금 브랜치가 기본 브랜치(main/master)이면 멈추고 작업 브랜치를 만들자고 한다.
2. **남은 변경 확인**: `git status`에 커밋 안 된 변경이 있으면 멈추고 `/team-ai:commit`을 먼저 하자고 한다.
3. **대상 브랜치**: 인자가 있으면 그 브랜치, 없으면 저장소의 기본 브랜치. `git log --oneline <대상>..HEAD`로 이번 PR에 들어갈 커밋을 확인한다. 커밋이 없으면 멈춘다.
4. **검증 확인**: 이번 대화에서 `verify`를 돌린 결과가 있으면 그것을 쓴다. 없으면 `verify`를 먼저 돌릴지 묻는다. 실패한 검증이 있으면 PR 본문에 그대로 적는다. 숨기지 않는다.
5. **올리기**: `git push -u origin <브랜치>`. 승인 창이 뜨면 사용자가 승인한다. 강제 push는 하지 않는다. 거절되면 원인(권한, 원격이 앞섬)을 알리고 멈춘다.
6. **PR 만들기**: `gh`가 있고 로그인되어 있으면 `gh pr create --base <대상> --title ... --body-file <임시 파일>`. `--draft` 인자가 있으면 초안으로 만든다. `gh`가 없으면 아래 본문을 보여 주고, 웹에서 만드는 주소(`https://<호스트>/<저장소>/compare/<대상>...<브랜치>`)를 알려 준다.
7. **보고**: PR 주소 한 줄, 그리고 리뷰어가 먼저 볼 곳 1~3개.

## 본문

저장소에 PR 템플릿(`.github/pull_request_template.md` 등)이 있으면 그 칸을 채운다. 없으면 이 형식을 쓴다.

```markdown
## 왜
<이 변경이 필요한 이유 1~3줄. 관련 이슈가 있으면 Closes #번호>

## 무엇이 바뀌나
- <사용자나 다른 개발자 입장에서 달라지는 것. 파일 목록이 아니라 동작으로>

## 확인한 것
- <실제로 실행한 검증 명령과 결과. 실행 안 한 것은 "확인 안 함">

## 리뷰어가 봐 줄 곳
- <테스트를 고친 곳, 설정·권한·의존성 변경, 판단이 갈리는 부분>
```

- 제목은 CLAUDE.md(가져온 AGENTS.md 포함)의 커밋 규칙 형식을 따른다. 커밋이 하나면 그 메시지를 쓴다.
- 커밋 메시지를 나열하지 않는다. 커밋 목록은 PR 화면에 이미 나온다.

## 규칙

- 병합, 리뷰 승인, 라벨·담당자 변경은 하지 않는다. 사용자가 요청한 경우만 예외다.
- 본문에 비밀값, 내부 주소, 고객 데이터를 넣지 않는다. diff에 보이면 멈추고 알린다.
- 테스트 파일이 바뀌었으면 "리뷰어가 봐 줄 곳"에 반드시 적는다.
