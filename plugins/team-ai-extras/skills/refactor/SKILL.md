# 리팩터링

$ARGUMENTS 를 리팩터링한다. **동작은 그대로, 구조만 바꾼다.**

## 0. 먼저 확인

- **왜 지금 하는가?** 실제 불편(버그 유발, 매번 수정이 어려움, 중복이 계속 어긋남)이 없으면 하지 않는다. "더 깔끔해 보여서"는 이유가 아니다.
- 요청 범위만 다룬다. 다른 개선거리는 목록으로 제안한다.

## 1. 안전망

- 이 코드를 검증할 수단이 있는지 확인한다: 테스트, 빌드, 실행 결과.
- 없으면 **현재 동작을 고정하는 테스트(특성화 테스트)를 먼저 만들자고 제안**한다. 자동 테스트가 어려운 영역(화면, 외부 장비·서비스 연동)은 수동 확인 절차를 글로 적어 두고 진행한다.
- 작업 트리가 깨끗한지 확인한다. 되돌아갈 지점이 있어야 한다.

## 2. 작은 단계

한 번에 하나씩 바꾸고, 단계마다 검증한다.

- 중복 제거: 새로 만들기 전에 기존 유틸이 있는지 먼저 찾는다. 두 번은 우연, 세 번이면 추출한다.
- 긴 함수 분리: 이름이 설명이 되게. 주석으로 설명해야 하면 이름이 틀린 것이다.
- 조건문 정리: 이른 반환으로 중첩을 줄인다.
- 죽은 코드: 주석 처리하지 말고 지운다. git 기록에 남아 있다.

## 3. 하지 말 것

- 나중에 필요할 것 같아서 만드는 인터페이스·제네릭·설정 옵션
- 동작 변경 끼워 넣기. 버그를 찾으면 따로 알리고 따로 고친다.
- 공개 시그니처·기존 테스트 깨기
- 한 커밋에 리팩터링과 기능 변경 섞기

## 4. 마무리

- 검증을 실제로 돌리고 결과를 보여 준다.
- 무엇이 어떻게 나아졌는지 1~3줄로 구체적으로 쓴다.
- 손대지 않은 개선거리를 목록으로 남긴다.
