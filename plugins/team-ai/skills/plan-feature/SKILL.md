# 계획 세우기

$ARGUMENTS 를 구현하기 전에 조사하고 계획을 세운다. 이 단계에서는 **코드를 고치지 않는다.** 수정하는 파일은 `plan.md` 하나다.

## 0. 시작 전 확인

`git status`로 커밋되지 않은 변경이 있는지 본다. 특히 세팅 파일(`CLAUDE.md`, `.claude/`, `plan.md`, `.vscode/`)이 커밋되지 않았으면, 계획을 세우기 전에 `/team-ai:commit`으로 먼저 정리하자고 알린다. 사용자가 그대로 진행하라고 하면 진행한다.

## 1. 조사

- CLAUDE.md의 구조·규칙을 확인한다.
- 이 저장소에서 **가장 비슷한 기존 구현**을 찾는다. 없으면 없다고 쓴다.
- 건드릴 파일과 영향 범위를 나열한다. 호출하는 곳까지 찾는다.
- 모르는 것은 모른다고 쓴다. 추측으로 채우지 않는다. 결과가 달라지는 모호함이면 질문 1~3개로 확인한다.

## 2. 선택지

방법이 하나면 그렇게 말하고 넘어간다. 둘 이상이면 비교하고 **하나를 추천**한다.

|---|---|---|---|

## 3. plan.md에 적기

`plan.md`의 "다음 작업 (구현 예정)" 섹션에 아래 형식으로 추가한다. 파일이 없으면 이 형식으로 새로 만든다. 같은 작업이 이미 있으면 합친다.

```
### [ ] 작업 제목
- 목표: 무엇이 되면 끝인가 (완료 기준. 확인 가능한 문장으로)
- 맥락: 왜 하는가
- 변경할 파일: 경로 — 무엇을
- 참조: 따라 할 기존 코드 경로
- 검증: 실행할 명령, 새로 추가할 테스트
- 안 하는 것: 범위 밖
- 멈춤 조건: 이럴 땐 멈추고 묻는다 (예: 스키마 변경이 필요해지면)
```

- 실제 파일 경로만 쓴다.
- 단계가 많으면 각각 따로 검증할 수 있는 작업 여러 개로 나눈다.

## 4. 승인 대기

계획 요약을 보여 주고 **멈춘다.** 사용자가 계획을 고치거나 승인하면 그때 구현한다. 사람이 엣지 케이스나 컨벤션을 보탤 수 있게 "고칠 점이 있으면 알려 달라"고 요청한다.

구현 중 계획과 달라지면 말없이 바꾸지 말고 알린 뒤 plan.md를 고친다. 끝나면 `verify`로 검증한다.
