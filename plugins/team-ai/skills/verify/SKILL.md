# 검증

"끝났다"고 말하기 전에 반드시 실행한다. 판단은 **실제 실행 출력**으로만 한다. "통과했을 것"이라고 쓰지 않는다.

## 1. 검증 명령 실행

1. CLAUDE.md의 **검증 명령** 섹션에서 명령을 찾는다. 없으면 package.json, Makefile, build.gradle, pyproject.toml 등에서 찾고, 찾은 명령을 알린다.
2. 순서대로 실행한다. 앞 단계가 실패하면 원인부터 본다.
   1. 타입체크 / 컴파일
   2. 린트
   3. 바뀐 부분과 관련된 테스트
   4. 시간이 허락하면 전체 테스트, 빌드
3. VS Code에서 실행 중이면 IDE 진단(`mcp__ide__getDiagnostics`)도 확인한다.
4. 실패하면 원인을 고치고 다시 실행한다. 같은 실패가 3번 반복되면 멈추고 보고한다.
5. 실행해서 확인할 수 있는 기능이면(CLI, API, 화면) 직접 실행해 출력을 본다.

## 2. 테스트 변경 감시

`git status --porcelain`과 `git diff`로 바뀐 파일 중 테스트 파일을 찾는다. 경로나 이름에 `test`, `tests`, `__tests__`, `spec`, `.test.`, `.spec.`, `_test.`, `Test.`이 들어간 파일이다.

- 테스트가 **삭제**됐거나, `skip`/`only`/`xit`/`@Disabled`/`pytest.mark.skip`이 추가됐거나, 기대값(assert, expect)이 바뀐 곳을 찾는다.
- 있으면 보고서의 "사람 확인 필요"에 파일과 줄을 적는다. 테스트를 통과시키려고 테스트를 바꾼 것인지 사람이 판단해야 한다.

## 3. 보고

```
## 검증 결과
- 타입체크: 통과 / 실패 (명령)
- 린트: 통과 / 실패
- 테스트: N개 중 N개 통과 (명령)
- 빌드: 통과 / 실행 안 함
- 직접 실행: (무엇을 실행했고 무엇을 봤는지)

## 사람 확인 필요
- 테스트 변경: 파일:줄 — 무엇이 바뀌었나

## 실패·건너뛴 항목
- (이유와 함께)
```

## 규칙

- 실행하지 않은 검증을 통과했다고 쓰지 않는다.
- 테스트를 지우거나 건너뛰게 바꿔서 통과시키지 않는다. 테스트가 틀렸다고 판단되면 먼저 묻는다.
- 실패 출력은 핵심 줄만 인용한다.
- 테스트 개수는 실행 출력에 나온 숫자로만 쓴다. 추가한 테스트 수는 작업 전후 실행 결과의 차이로 계산하고, 직접 세어 짐작하지 않는다.
- plan.md 항목의 "검증"에 적힌 내용이 있으면 그것도 실행한다. 통과하면 해당 항목을 `[x]`로 표시하고, 항목 전체(하위 내용 포함)를 "완료" 섹션 맨 위로 옮긴다.
